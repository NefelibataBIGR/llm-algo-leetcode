# 后训练与对齐正文

## 页面目标

这页把 `14-16 + 50 + 84-85` 串成一份可执行清单，重点是：

- 后训练为什么要在 SFT 之后继续做
- PPO、DPO、GRPO 各自改什么
- 偏好数据和评测怎么接到方法上
- 什么时候该走项目页，什么时候只需要机制理解

## 常见检查项

| 检查项 | 你要确认什么 | 常见问题 |
|:---|:---|:---|
| 方法谱系 | PPO、DPO、GRPO 是否分清楚 | 把三种方法混成“对齐”一个概念 |
| 数据形态 | chosen / rejected / group candidates 是否匹配方法 | 数据对和方法不匹配 |
| 训练代价 | 系统对象和显存 / 计算代价是否说清楚 | 只看 loss，不看训练复杂度 |
| 评测口径 | win-rate、pairwise accuracy、judge score 是否一致 | 评测指标各说各话 |
| 项目闭环 | 是否能输出 accept / tune / reject | 只有方法，没有决策 |

## 常见失败模式

- DPO 学成了“看起来像 SFT”，但没有真正用偏好对。
- GRPO 的组内候选构造不稳定，导致训练结果波动大。
- PPO 讲了很多，但没有把系统代价和四模型链路说清楚。
- 数据看起来能跑，但评测口径和训练目标不一致。
- 项目页只给指标，没有给最终采用建议。

## 方法对照

| 方法 | 解决什么 | 代价是什么 | 更适合什么时候用 |
|:---|:---|:---|:---|
| PPO / RLHF | 经典对齐路线，系统闭环完整 | 训练链路重、对象多 | 需要完整 RLHF 语义时 |
| DPO | 用更轻的方式做偏好优化 | 依赖高质量偏好对 | 想快速做项目化落地时 |
| GRPO | 组内比较，更适合生成类对齐 | 依赖 group-wise 候选 | 需要组内排序/相对优势时 |

## 数据与评测

| 数据 / 评测 | 关注点 | 常见误区 |
|:---|:---|:---|
| chosen / rejected | 两个答案谁更好 | 样本对不干净 |
| group candidates | 同一 prompt 下多个候选 | 组内样本构造不稳定 |
| win-rate | 最终偏好胜率 | 只看单一指标 |
| pairwise accuracy | 两两偏好判断是否一致 | 忽略数据噪声 |
| judge score | 模型/人工评审分数 | 评测标准不统一 |

## 小结

后训练不是 SFT 的附属，它是一条独立的对齐方法线；真正重要的是把方法、数据、评测和项目决策串起来。
