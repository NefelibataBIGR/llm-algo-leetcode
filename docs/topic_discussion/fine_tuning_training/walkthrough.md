# 监督微调（SFT）闭环深入阅读

## 主故事线

一条完整的 SFT 故事，可以按下面的顺序读：

`prompt/response sample -> data trio -> response-only loss -> LoRA adapter -> scheduler/accumulation -> eval -> project report -> final decision -> visual assets -> advanced SFT placeholder`

这条线的重点不是某个 API，而是把样本如何一步步变成可验证的训练结论，再把基础闭环自然过渡到进阶场景。

## 基础层：先跑通第一个闭环

### 1. 从一条样本开始

先拿一条 `prompt / response` 样本，确认它是否适合进入训练集。

- 是否需要 system / user / assistant 角色
- response 是否完整
- 是否存在空样本、重复样本或脏格式

### 2. 把样本变成训练三件套

进入 `01` 后，重点确认：

- `input_ids` 是否正确拼接
- `attention_mask` 是否正确屏蔽 padding
- `labels` 是否只对 supervision 区间计 loss

这一步决定后面训练曲线有没有意义。

### 3. 接上 LoRA

进入 `02` 后，重点不在“有 LoRA”，而在：

- 挂载到哪些层
- `r / alpha / dropout` 怎么配
- 可训练参数占比是多少

如果需要更小显存，可以在这里顺手对照 `26`。

### 4. 让训练控制口径一致

进入 `03` 后，要统一三件事：

- scheduler 按什么步数更新
- optimizer 什么时候 step
- effective batch 到底是多少

这一步是很多“看起来能跑”的实验最后出问题的地方。

### 5. 做端到端实验和验证

进入 `04` 后，不要只看 train loss。

至少要确认：

- train / val 是否分开
- 周期性评估是否正常触发
- 生成样例有没有变化

如果条件允许，再补少量人工检查样例或更明确的指标。

### 6. 回到项目页做交付

进入 `05` 后，故事才算结束。

这里要回答的不是“能不能训”，而是：

- 数据是否可信
- loss 口径是否正确
- adapter 和 tokenizer 是否可交付
- 结果是否值得采用

### 7. 看图册收口

进入 `06` 后，把前面所有环节放回图里复盘：

- 数据对齐是否清楚
- LoRA 和训练控制是否互相打架
- 项目决策图是否能一眼说明采用理由

这页不是新增概念，而是把基础闭环压成可视化资产。

## 进阶层：基础闭环之后再分化

基础闭环跑通后，再进入 `30 -> 31 -> 32` 的进阶占位：

- `30` 看长上下文微调，确认 token 预算、窗口和截断策略是否合理
- `31` 看 LoRA 变体，确认不同 adapter 设计到底解决什么问题
- `32` 看数据工程，确认数据清洗、采样和格式是否真的稳定

这一步的意义是把“能跑”推进到“在特定场景下更稳、更省、更可控”。

## 典型分支

### 分支 1：数据不干净

先停在 `01`，不要急着改 LoRA 或 scheduler。  
数据有问题时，后面的结论大概率不可信。

### 分支 2：显存不够

先看 `02 -> 26 -> 05`，确认是需要更小 batch，还是需要换成 QLoRA 路径。  
不要先把训练流程改乱。

### 分支 3：loss 正常但样例不好

先回到 `04 -> 05`，看是不是评估样例太少、数据分布太窄，或者 LoRA 挂载层不合适。

### 分支 4：基础闭环已经跑通，但场景不够

再进入 `30 -> 31 -> 32`，看是不是需要长上下文、LoRA 变体或更细的数据工程。

## 阅读建议

1. 先从一条样本看 `01`。
2. 再看 `02`，理解 LoRA 是怎么挂进去的。
3. 再看 `03`，把训练控制口径统一。
4. 再看 `04`，把实验闭环跑通。
5. 最后看 `05`，把机制变成项目结论。
6. 跑通基础闭环后，再看 `30 -> 31 -> 32` 的进阶分支。
