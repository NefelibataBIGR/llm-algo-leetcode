# Profiling 深入阅读

## 主故事线

profiling 最典型的一条故事线不是“发现一个热点”，而是：

`感觉变慢 -> 采证 -> 归因 -> 交叉验证 -> 决策是否要改`

这条线的重点在于：很多优化不是因为“看到了一个红色条”就该做，而是因为有一整条证据链支持它。

## 1. 先问问题，而不是先开工具

profiling 的第一步不是打开 profiler，而是先问：

- 这次问题是变慢、爆显存，还是多卡收益不稳？
- 我要证明的是单个 kernel 问题，还是系统级问题？

只有问题先立住，后面采集哪些证据才不会失控。

## 2. 先看时间，再看空间

大多数性能问题，先从 `02` 看时间热点、operator table 和 trace。
如果时间问题又和 memory 波动一起出现，再进入 `03` 看 residency 和 allocation。

## 3. 如果跨卡，再看等待

一旦问题扩到多卡，不再只是“哪个算子慢”，而是“谁在等谁”。  
这时 `04` 的 wait / overlap / communication trace 才是重点。

## 4. 最后回到验证和决策

很多优化最大的失败点，不是在诊断，而是在验证：

- benchmark 口径不统一
- 回归样本不稳定
- before / after 其实不可比

所以 `05 -> 06` 负责把 profiler 证据变成最终行动建议。

## 阅读建议

1. 第一次读，按 `01 -> 02 -> 03 -> 04 -> 05 -> 06`。
2. 已经有 trace 但不会解释，先读 `02 -> 03 -> 04`。
3. 已经做过优化但不确定是否成立，直接读 `05 -> 06`。
